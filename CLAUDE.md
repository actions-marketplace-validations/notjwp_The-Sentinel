# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Python 3.13+ is required. The virtualenv lives in `.venv/` (activate with `.venv\Scripts\Activate.ps1` on Windows).

Dependencies are **split**: `requirements.txt` is runtime-only; dev/test/lint/mutation tooling lives in `requirements-dev.txt` (which pulls in the runtime set via `-r requirements.txt`). Install the dev file for development — a plain `pip install -r requirements.txt` will not have `pytest`/`ruff`/`mutmut`.

```bash
# Install dev dependencies (tests, lint, mutation — includes runtime deps)
pip install -r requirements-dev.txt

# Run the API (dev)
uvicorn main:app --reload

# Run the full test suite (config in pyproject.toml, testpaths = sentinel/tests)
pytest

# Coverage (branch)
pytest --cov=sentinel --cov-branch --cov-report=term-missing

# Lint (ENFORCED in CI; run locally before pushing)
ruff check sentinel main.py

# Mutation testing (targets domain/application/infrastructure)
mutmut run && mutmut results
# or containerized:
docker build -f mutation.Dockerfile -t sentinel-mutmut . && docker run --rm sentinel-mutmut

# Build & run the production container
docker build -t sentinel:dev . && docker run --rm -p 8000:8000 sentinel:dev
# or: docker compose up --build
```

## Architecture

Clean Architecture, strictly layered. The dependency rule (domain imports nothing from
FastAPI/sklearn/infrastructure) is **enforced by tests** in `sentinel/tests/hardening/test_architecture_extended.py` — breaking it fails CI, not just review.

- **domain/** — pure logic: `Finding`/`PullRequest` entities, `SeverityLevel` value object, and the three analysis services (`debt_service`, `security_service`, `semantic_service`). Semantic depends on an `EmbeddingPort` Protocol implemented in infrastructure (dependency inversion).
- **application/** — `RiskEngine` (aggregates the three engines) and `AuditOrchestrator` (LLM enrichment, document findings, markdown report building, translation). Ports for LLM/document services are declared as `Protocol`s here, not concrete imports.
- **infrastructure/** — `semantic/embedding_engine.py` (sklearn `HashingVectorizer`, 128-dim, L2-norm, deterministic/stateless), `llm/` (provider abstraction + NVIDIA NIM provider), `github/github_client.py` (GitHub App JWT → installation token → PR comment; list endpoints are paginated, capped at `MAX_LIST_PAGES`), `redis/` (durable `RedisJobQueue` + `RedisDeliveryDeduper`, selected by `REDIS_URL`).
- **api/** — FastAPI controllers (`webhook`, `health`, `metrics`) + `delivery_dedup.py` (in-memory X-GitHub-Delivery dedup). **workers/** — async `JobQueue` (FIFO, in-memory) + `BackgroundWorker` loop. The composition root (`main.py`) swaps `JobQueue` for `RedisJobQueue` when `REDIS_URL` is set; both share the `enqueue`/`dequeue`/`ack`/`recover_pending` surface (no-ops on the in-memory one).
- **action/** — the third delivery mechanism, beside the webhook and the queue: `context.py` (pure parsing of the Actions environment) + `runner.py` (composition root, exit codes, job summary) + a `__main__.py` shim run as `python -m sentinel.action`. Packaged by `action.yml` as a **composite** action with the narrower `requirements-action.txt` (no fastapi/uvicorn/redis — a server import creeping in is caught by the `action-smoke` CI job).

### Request pipeline — one mode: identify a PR, queue it

`POST /webhook` (`sentinel/api/webhook_controller.py`) runs signature -> event filter -> delivery dedup -> enqueue, and answers 200 for every outcome (GitHub records any non-2xx as a failed delivery). It **never analyzes caller-supplied code**:

The route identifies a pull request (directly-supplied `repo`/`pr_number`/`author`/`files`, else the nested GitHub event body via the `_extract_*` helpers, assembled by `_build_job`) and enqueues it; `BackgroundWorker` later fetches the PR's real diff from GitHub, runs `RiskEngine.assess_resilient`, LLM-enriches the security findings, and posts a structured `AuditOrchestrator.build_report` back via `GitHubClient.upsert_comment`. This is the only path where the **semantic engine is wired in** (the worker constructs `RiskEngine(semantic_service=...)`; since M5 it compares the PR against a real corpus fetched from the base ref — note `detect_duplicates` embeds the *whole* PR against each corpus chunk, so it catches "the PR mostly duplicates an existing unit", not one copied function buried in a large PR).
   - **Code fetch (M1, extended in M3/M5):** when the job carries `owner`/`repo`/`pr_number` and GitHub is enabled, `BackgroundWorker._fetch_pr_data` calls `GitHubClient.get_pull_request_data` → `GET /pulls/{n}/files` (paginated), keeping each patch's **added (`+`) lines** as the code to analyze and threading `files`/`file_contents` into the job so the worker's `run_full_review` carries documentation findings — full parity with the sync path. **M5:** doc files (`.md`/`.txt`) get their FULL text via each item's `contents_url` (patch text is only the fallback on fetch failure), and `_fetch_pr_data` also builds the **semantic corpus** from the PR's base ref (`get_pull_request_refs` → `get_repo_code_corpus`, i.e. `GET /pulls/{n}` → `git/trees?recursive=1` → `git/blobs`, capped by `CORPUS_MAX_FILES`/`CORPUS_MAX_FILE_BYTES`, cached per ref), chunks it into top-level units via `SemanticService.chunk_code_units`, and threads it as `job["existing_code_list"]` (capped at `CORPUS_MAX_UNITS`). **M8:** with no real corpus (owner-less job, corpus fetch failed) the semantic engine is **skipped outright** — the old static `EXISTING_CODE_LIST` two-function fallback is gone, because a placeholder corpus could cross the 0.9 threshold and fabricate a HIGH. The queued payload now threads an **`owner`** key (derived via `_extract_owner`, or split from an `owner/name` repo); without an owner the fetch/post are skipped and the worker analyzes whatever `code` the job holds (usually empty). `GitHubClient._http_json` discards JSON arrays, so PR-file listing uses a separate `_http_json_list` primitive.
   - **LLM enrichment + idempotent post (M2):** the worker now builds its orchestrator with an `LLMService` (via the module-level `bw_module._build_llm_service` seam, mirroring `webhook_controller.get_llm_service`) and runs `enrich_findings_with_llm` on the security findings before `build_report`, so async reviews carry explanations/fixes just like the sync path (inert with no `NVIDIA_API_KEY` — falls back to static strings, no network). Both paths post via `GitHubClient.upsert_comment`, which embeds a hidden `SENTINEL_COMMENT_MARKER` (`<!-- sentinel-review -->`) and **updates Sentinel's existing PR comment in place** (list → PATCH) instead of stacking a new comment on every re-run; `post_comment` remains the unchanged create-only primitive it composes.
   - **Check runs (M6):** after the comment, the worker also posts a native **check run** (`GitHubClient.create_check_run`, name `Sentinel AI Code Review`) when `ENABLE_CHECKS` (default true) and the job carries a `head_sha` (stashed by `_fetch_refs`, which **M8 moved ahead of the file fetch** so the SHA exists even when the file fetch is what failed). Conclusion mapping: CRITICAL/HIGH → `failure`, MEDIUM → `neutral`, LOW → `success`. Inline annotations come from `AuditOrchestrator.build_check_payload`: doc findings use their own `file`/`line`; security findings resolve through the job's **`line_map`** (one `(path, head_line)` pair per assembled-code line, built from patch hunk headers by `_added_lines_with_positions`); semantic findings are summary-only. Capped at 50 annotations (API limit). Requires the app permission **Checks: Read & write** — without it the POST fails safely (`check run=False` logged) and only the comment lands. Each review posts a fresh run (no upsert).
   - `BackgroundWorker.process_job` still returns the pinned one-liner `PR #<n> Risk: <SEV>`; it and `start()` share `_assess` (single assessment) + `_format_risk_line`.
**Removed in M9: the synchronous `code`-in-body mode.** A `code` field used to switch the endpoint into running the engines over caller-supplied source inline. It made a public endpoint an arbitrary-code-analysis service, real GitHub deliveries never carried the field, and it was scheduled for removal back in M1. `WebhookPayload` no longer declares `code`, so it is dropped by `extra="ignore"`; `_run_sync_review`, `_webhook_impl`, `_resolve_override`, `_resolve_override_if_present`, `_extract_file_contents` and the five per-request dependency getters went with it (601 -> 249 lines). The manual-`dependency_overrides` quirk documented below is gone with them — only `get_orchestrator` remains, injected in `main.py`.

`RiskEngine.assess` raises on engine failure; `assess_resilient` swallows failures and returns safe defaults. Use the resilient variant for anything running in the background.

### Things that will surprise you

- **One deployment serves many installations.** `installation.id` is read off the delivery by `webhook_controller._extract_installation_id`, threaded as `job["installation_id"]`, and used by `BackgroundWorker._client_for` to pick a per-installation `GitHubClient` from a bounded cache (`MAX_CACHED_CLIENTS = 32`). Clients are cached, not rebuilt, because the installation token lives **on** the client — a fresh one per job would mint a token per PR. A job with no installation id falls back to `GITHUB_INSTALLATION_ID`, which is what keeps manual triggers and `e2e.py` working. The hop that fails silently is the middle one: `AuditOrchestrator.enqueue_pull_request` rebuilds the job from a **whitelist**, so a new key added at the webhook and not there vanishes with nothing logged.
- **The review pipeline is `run_review`, a module-level function in `background_worker.py`** — not a method. `BackgroundWorker._process_one` is a one-line delegate. It lives at module scope so the GitHub Action can run the identical fetch → assess → post flow without constructing a worker and a queue it would never use. It returns a `ReviewOutcome` (`severity`, `report`), where `severity is None` means the review was **skipped**, which is deliberately not the same as LOW.
- **`GitHubClient` has two auth modes.** `access_token` (set via `GitHubClient.from_access_token`) short-circuits `_get_installation_token()` and is used by the Action, where the runner supplies a `GITHUB_TOKEN` and there is no app to sign as. `_token_headers` already emits `Authorization: token …`, which is correct for both, so nothing else changed. The method name is now a slight misnomer; it is not renamed because ~28 tests patch that exact attribute.
- **The Action's client builder ignores `ENABLE_GITHUB` on purpose** (`sentinel/action/runner.py`). On a runner, being handed a token *is* the enablement signal — and CI sets `ENABLE_GITHUB=false` globally, so gating there would disable the thing under test while the suite still passed.
- **`head_sha` comes from the event payload, never `GITHUB_SHA`.** On `pull_request` that env var is the synthetic merge commit (on `pull_request_target`, the base commit); a check run attached to either is invisible on the PR.
- **The webhook has exactly one injected dependency.** `get_orchestrator`, overridden in `main.py` via `app.dependency_overrides` and in tests the same way. The old manual-override resolution (`_resolve_override`, which read `request.app.dependency_overrides` by hand because plain `Depends` didn't reach the sync path) is gone along with that path — plain `Depends` is all there is now.
- **Report/translation logic lives in `AuditOrchestrator`**, not a separate service. `build_report`, `append_translations`, `enrich_findings_with_llm`, and `collect_document_findings` are all methods on the orchestrator. (Older `report_service.py`, `translation/translator.py`, `llm/openai_provider.py`, and the `use_cases/process_pull_request.py` module were removed/merged — ignore references to them in README.md / PROJECT_CONTEXT.md.)
- **LLM findings are matched by object identity.** `enrich_findings_with_llm` keys the provider response on `id(finding)`. `Finding` is a `frozen=True` dataclass, so enrichment produces new instances via `dataclasses.replace` rather than mutation.
- **`Finding` uses `finding_type` but exposes a `.type` property.** Report/serialization code compares `finding.type == "security"` / `"documentation"`.
- **LLM provider is NVIDIA NIM, not OpenAI.** `NIMProvider` uses the `openai` SDK pointed at `https://integrate.api.nvidia.com/v1` with `deepseek-ai/deepseek-v4-flash`. The credential env var is `NVIDIA_API_KEY`. All LLM/GitHub calls are failure-safe: on any error they fall back to static strings / skip, never crash the request.
- **Webhook signature verification** lives in `sentinel/api/webhook_security.py`, wired as a route dependency on `POST /webhook`. It enforces the `X-Hub-Signature-256` HMAC **only when `GITHUB_WEBHOOK_SECRET` is set** (so the test suite, which sets no secret, is unaffected); otherwise it's skipped. It compares as **bytes** (`hmac.compare_digest` on encoded values) so a malformed/non-ASCII header returns 401 rather than raising a 500.
- **Webhook deliveries are deduped by `X-GitHub-Delivery`.** The route answers repeats (within a 10-min TTL) with HTTP 200 `{"status": "duplicate"}` and no re-processing; requests without the header are never deduped. The module-level `webhook_controller._deduper` comes from `_build_deduper()`: Redis-backed when `REDIS_URL` is set, else in-memory. `is_duplicate` is **async on both** implementations (interface parity); the in-memory body never awaits. Tests monkeypatch `webhook_controller._deduper` with a fresh instance.
- **Security analysis uses two engines, chosen per file.** `ASTSecurityService` (`domain/services/ast_security_service.py`, stdlib `ast` only) analyzes a changed `.py` file when its FULL source was fetched and parses; `SecurityService` (regex) handles everything else. The split exists because the worker's assembled `code` is *added lines only* — an indented method body or a single line from inside a function does not parse, so an AST engine alone would fail on most real PRs while regex tolerates fragments. `analyze_source` returns `None` for unparseable input, deliberately distinct from `[]`, because "could not look" and "looked, found nothing" drive different fallbacks. The worker runs the AST pass first (`_ast_security_findings`), records which files it covered, then `_strip_ast_covered_lines` removes those files from the regex blob **and from `line_map` in lockstep** — so no line is ever reported by both engines and no de-duplication guesswork is needed. AST findings carry a real `file`/`line`, so `build_check_payload` annotates them directly; only regex findings still resolve through `line_map`. Findings are filtered to lines the PR actually added: the analyzer sees the whole module, and reporting pre-existing problems would be accurate but not the author's business. Full `.py` source costs one API call per file, capped by `MAX_SOURCE_FETCHES`.
- **Only some GitHub events are reviewed (M8).** `sentinel/api/webhook_events.py::should_process` gates on `X-GitHub-Event`: `pull_request` with an action in `REVIEWABLE_ACTIONS` (`opened`/`synchronize`/`reopened`/`ready_for_review`) is processed; `ping`, every other event, and every other action are answered HTTP **200** `{"status": "ignored"}` with no work done. Like the webhook-secret gate, it only applies **when the header is present** — no `X-GitHub-Event` means no filtering, which is why the whole pre-M8 test suite is unaffected. It runs **before** the delivery dedup, so an ignored event never burns a dedup slot.
- **A failed PR fetch reports a skipped review, not a clean one (M8).** `_fetch_pr_data` returns a bool; `False` **only** when a fetch that should have happened raised. On `False` the worker skips assessment and the comment entirely and posts a `neutral` check run titled "Review skipped" (`_post_fetch_failure`), counting `sentinel_reviews_skipped_total{reason="fetch_failed"}`. Note the distinction that makes this correct: **empty code is not a failure** — a docs-only PR legitimately has zero added code lines and still gets a full review.
- **The worker loop paces only on failure (M8).** `asyncio.sleep(ERROR_BACKOFF_SECONDS)` lives in the `except` branch; the success path has no delay because both queues already block/poll inside `dequeue()`. Shutdown is graceful: `start()` runs process-and-ack as one `asyncio.shield`ed unit and **awaits it in the `CancelledError` handler** before re-raising, so a cancel mid-job still acks and orphans no task; `main.py` bounds that wait with `SHUTDOWN_GRACE_SECONDS`.
- **Metrics are hand-rolled, not `prometheus_client` (M7).** `sentinel/monitoring/metrics.py` holds a module-singleton `MetricsRegistry` (thread-safe counters/gauges/summaries; **every method swallows its own errors** — instrumentation must never fail a review). `GET /metrics` (no flag, always on like `/health` — firewall it in public deployments) renders Prometheus text format; queue depth is computed live via `app.state.job_queue.depth()` (both queues implement it; Redis returns -1 on error). Series: `sentinel_jobs_processed_total`, `sentinel_reviews_total{severity}`, `sentinel_webhooks_total{mode}`, `sentinel_llm_calls_total{outcome}`, `sentinel_github_posts_total{kind,outcome}`, `sentinel_redis_errors_total{op}`, `sentinel_job_duration_seconds` (summary), `sentinel_queue_depth` (gauge). Tests call `metrics.reset()` then assert on `snapshot()`.
- **Redis outages back off and stay quiet.** `RedisJobQueue.dequeue` doubles its retry sleep per consecutive failure up to `MAX_BACKOFF_SECONDS` (5s) and logs ONE traceback per failing streak, then at most one summary line per `LOG_SUPPRESS_SECONDS` (60s), plus a single "reconnected" line on recovery.
- **Queue durability is opt-in and at-least-once, with bounded retries.** With `REDIS_URL` set, jobs live in a Redis list (`sentinel:jobs`); `dequeue` LMOVEs to a processing list, the worker `ack`s after completion, and `recover_pending()` (run at worker start) re-queues whatever a crashed worker left behind. A crash between posting and acking re-runs the job — safe because `upsert_comment` is idempotent. **M8:** the envelope carries an `attempts` count (on the envelope, never inside the job dict); each recovery bumps it, and a job that burns `MAX_ATTEMPTS` (3) is parked on `sentinel:jobs:dead` instead of being resurrected forever. `recover_pending()` still returns the **re-queued** count only. A *hung* (rather than crashed) worker still strands its job until the next restart — that needs a visibility timeout, deliberately not built yet. With `REDIS_URL` unset nothing changes: in-memory queue, jobs lost on restart.

### Feature flags (`sentinel/config/settings.py`, read from `.env`)

Read settings only via `get_settings()`. **`ENVIRONMENT`** (default `development`) sets the deployment posture: `production` makes `GITHUB_WEBHOOK_SECRET` **mandatory** — `main.verify_startup_config` raises at boot when `ENABLE_GITHUB` is on without it, so a misconfigured deploy fails loudly rather than serving an unsigned webhook (it runs *before* the worker task is created, so a failure orphans nothing). **`METRICS_TOKEN`** (default unset) gates `GET /metrics` behind `Authorization: Bearer <token>`; unset leaves it open, which is the dev default and why the test suite is unaffected. Other defaults: `ENABLE_LLM=true`, `ENABLE_GITHUB=true`, `ENABLE_CHECKS=true` (needs the app's Checks:write permission to actually post), `ENABLE_DOC_REVIEW=true`, `ENABLE_TRANSLATION=false`, `LLM_MAX_CALLS=1`, `LLM_TIMEOUT=5.0`, `REDIS_URL` unset (in-memory queue/dedup; set it — e.g. `redis://localhost:6379/0` — for durable, restart-surviving state; docker-compose wires `redis://redis:6379/0`). GitHub/LLM are effectively inert without their credentials even when flag is on (LLM requires a resolved `LLM_API_KEY`). **Translation is real but budget-gated:** `append_translations` → `LLMService.explain_issue_safe` shares the `LLM_MAX_CALLS` budget with enrichment, so with the default `1` translations always skip — enabling them for real means `ENABLE_TRANSLATION=true` **and** `LLM_MAX_CALLS>=3` (1 enrichment + 1 per language). `GITHUB_WEBHOOK_SECRET` (default unset) gates webhook signature verification — see the note above; in production set it, or the endpoint accepts unsigned requests (a startup warning fires when `ENABLE_GITHUB` is on without it).

**LLM provider is env-configurable (any OpenAI-compatible endpoint).** `LLM_BASE_URL` (default `https://integrate.api.nvidia.com/v1`), `LLM_MODEL` (default `deepseek-ai/deepseek-v4-flash`), and `LLM_API_KEY` are threaded `Settings → LLMService → NIMProvider` (whose class constants are only fallbacks). `LLM_API_KEY` **falls back to `NVIDIA_API_KEY`** when unset (back-compat), and the LLM-enabled gate is `ENABLE_LLM and bool(LLM_API_KEY)`. Switching providers (a working NVIDIA model, Groq, Gemini, Ollama…) is a `.env` change, no code edit — see `.env.example` for ready presets. `NIMProvider` is a misnomer now: it's a generic OpenAI-compatible client, not NVIDIA-specific.
